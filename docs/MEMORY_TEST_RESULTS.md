확인한 시나리오에서는 게임 객체의 지속적인 누적이 관찰되지 않았습니다.

## 방법

Release/net10.0, 같은 Windows PC의 서버·Python 클라이언트·Docker MySQL 8.4 및 Redis 7.4.  
세션 풀 100개, 동시 로그인 60명으로 준비 3회 후 측정 50회를 반복했습니다.

회차마다 로그인 → 각 사용자 Hero 조회 10회·변경 10회 → 매칭 참가·취소·재참가·성립 → 한쪽 연결 종료와 상대 알림 확인 → 모든 연결 종료를 수행했습니다.  
준비 포함 로그인 3,180회, Hero 조회·변경 각각 31,800회, 매칭 성립·상대 종료 확인 1,590회입니다.

회차 종료 후 활성 세션·등록 유저·매칭 대기·방·유저별 방 인덱스·정리/종료 대기·DB 대기 작업이 0, 유휴 세션이 100인지 확인했습니다.  
DB 수치는 실행 중 작업이 아닌 큐의 대기 작업 수입니다.

테스트 전용 startup hook으로 500ms마다 관찰했고, dotnet-gcdump 10.0.750501로 준비 후·매 10회 후·마지막 무부하 30초 후 총 7회 수집했습니다.  
덤프 수집은 Gen2 GC를 유발하므로 자연 GC 상태의 성능 측정과 구분합니다. 관찰 코드의 메모리도 포함됩니다.
